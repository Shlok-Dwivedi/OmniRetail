# DAV practical review and implementation map

Reviewed the notebooks, PDF text, and Word document text in **all nine practical directories (Lab 0–8)**, including alternative assignment versions. The extracted source evidence is retained in `lab-source-analysis.txt`. Some PDFs contain only image pages; their text extraction is empty, so notebook/document counterparts were used rather than claiming OCR of screenshots. Root-level assignment documents duplicate materials in the practical directories. The original practical files are unchanged.

The practicals teach a progression from Python/dataframe foundations through ingestion, cleaning, API integration, relational ETL, preprocessing, modeling, time series, and visualization. OmniRetail retains that progression and the original retail analysis goal. It does not copy student/employee/weather datasets into unrelated customer-facing screens.

## Defects found in the starting project

1. The only product was a Streamlit script with no requirements files, no web-service boundary and no reproducible cross-platform setup.
2. All standalone analytical entry points used an absolute `E:\SEM_Pracs\...` path.
3. Documentation said CSV/XML/JSON were integrated, while the ETL only read XLSX. The synthetic auxiliary orders had an incompatible schema and were not joined to the retail data.
4. Fixed currency multipliers and synthetic macro data were described as API integration. Neither had a truthful rate date or network failure path.
5. Duplicate lines were retained; missing identifiers, invalid dates and non-finite inputs were not validated consistently. Guest users could be counted as a registered customer in some summaries.
6. Invoice cancellation signs were not normalized consistently, which could overstate signed refund value for a positive-quantity cancellation source.
7. RFM `qcut` could fail on tiny datasets or tied values. Frequency ties were split arbitrarily by row order.
8. The “CLV” regression used same-period average order value to explain same-period spend. AOV × frequency is the target itself; its impressive score was not forward predictive evidence.
9. Time series lacked short/constant-data guards and a benchmark. Forecasting was recomputed repeatedly in the UI. A holiday explanation for the peak was asserted without evidence.
10. The Excel file contained formatted tables but no actual chart objects. Downloads depended on pre-generated files rather than current filters.
11. Tests mostly asserted that pre-existing files existed and a particular model score was high. They did not verify business workflows, ingestion failures, persistence or the interface.
12. Hard-coded record counts/model metrics in the README and notebook could become stale. Some counts already disagreed with the data.

The revised product addresses these through shared services rather than separate calculations for notebook, browser, and exports. Architectural tradeoffs and measured validation are documented in `ENGINEERING.md`.
